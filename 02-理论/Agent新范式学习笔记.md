## MCP 协议

### 概念

MCP（Model Context Protocol）是 2025 年 10 月 Anthropic 发布的开源协议，核心思想是把 LLM 的「能力扩展」从硬编码的工具函数调用，升级为可插拔的「服务器-客户端」连接架构——就像 USB 接口让电脑可以随时接入新设备一样，MCP 让 LLM 可以随时接入新的数据源和执行工具，且无需修改模型本身。

### 核心机制

| 维度 | 说明 |
|---|---|
| **架构** | 客户端（LLM 集成） ↔ 传输层（SSE/Streamable HTTP） ↔ 服务器（资源+工具+提示词提供者） |
| **三层模型** | 资源（Resources，数据读取，如文件/数据库）、工具（Tools，执行操作，如搜索/计算）、提示词（Prompts，对话模板） |
| **传输层** | 支持 SSE（Server-Sent Events）用于流式传输，以及 Streamable HTTP 用于请求-响应式交互 |
| **协议定位** | 协议层的中间件——负责连接客户端和服务器，具体逻辑由服务器实现 |
| **标准化意义** | 统一了不同 LLM 平台的工具集成方式，一个 MCP 服务器可同时服务 Claude、OpenAI、GPT-4 等 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| MCP Server | 提供资源、工具、提示词的服务端，运行在本地或远程 |
| MCP Client | LLM 集成中的 MCP SDK 客户端，发起调用并处理响应 |
| Resource | 数据读取接口，通过 `resources/read` 调用，返回结构化数据 |
| Tool | 工具调用接口，通过 `tools/call` 调用，支持 JSON Schema 参数定义 |
| Prompt | 预定义对话模板，通过 `prompts/get` 加载，用于批量/批量操作 |
| 流式传输 | 大文本响应通过 SSE 流式推送，避免一次性返回大量文本 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| MCP SDK（Anthropic） | 官方 Python/TypeScript SDK | 提供 `create_server`、`MCPClient`、`StreamableHTTPClient` 等核心接口 |
| LangChain MCP | LangChain 集成层 | 通过 `LangChainMCP` 适配器桥接 LangChain 工具链 |
| 官方服务器 | Python `mcp.server` | 装饰器模式定义工具/资源，如 `@mcp.tool()`、`@mcp.read()` |

### 要点速记

- MCP 是「工具即插即用」的协议层，不是模型层——模型本身不改变
- 三层模型：资源（读）、工具（写）、提示词（模板）——覆盖 LLM 所有外部交互
- 传输层支持 SSE 流式，解决大文本响应延迟问题
- 一个 MCP 服务器可同时服务多个 LLM 平台（Claude、OpenAI、GPT-4）
- 与工具调用的关系：MCP 是工具调用的「标准化传输协议」，底层还是函数调用

## A2A 协议

### 概念

A2A（Agent-to-Agent）协议是 2025 年 12 月 Google DeepMind 联合多家企业发布的开源标准，核心思想是让「多智能体协作」从硬编码的函数调用，升级为可互操作的协议层——就像互联网协议让不同公司网站能互相访问一样，A2A 让不同厂商的 AI 智能体能互相发现、对话、协同完成任务。

### 核心机制

| 维度 | 说明 |
|---|---|
| **协议定位** | Agent 层（上层）——定义智能体间如何发现和互相访问，不规定具体执行逻辑 |
| **发现机制** | 通过 `well-known` 目录（类似 DNS 目录）发现可用的 Agent 服务 |
| **传输层** | 基于 HTTP 和 JSON-RPC，每个 Agent 暴露标准 HTTP 端点 |
| **协议内容** | 包含 Agent 发现（Discovery）、会话管理（Session）、消息传递（Messaging） |
| **标准化意义** | 不同厂商的 Agent（如 Claude、Gemini、本地 Agent）可跨平台协作 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| Agent Node | 运行 A2A 协议的智能体服务，暴露 `well-known` 端点 |
| well-known 目录 | 标准路径 `/.well-known/a2a.json`，列出该 Agent 支持的能力 |
| Session | Agent 间的工作会话，通过 `startSession` 创建 |
| Task | Agent 间传递的协作任务，包含目标、子任务、状态 |
| JSON-RPC | 消息传递的传输协议，基于 HTTP POST |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| A2A SDK（Google） | 官方 Python/TypeScript SDK | 提供 `AgentClient`、`AgentServer`、`Task`、`Session` 等核心接口 |
| OpenAI A2A | OpenAI 平台集成 | 通过 A2A 协议实现 GPT-4 与外部 Agent 的协作 |
| Anthropic MCP + A2A | MCP 工具 + A2A 发现 | MCP 负责工具连接，A2A 负责 Agent 间发现，两者互补 |

### 要点速记

- A2A 是「多智能体协作」的互联网协议——让不同厂商的 Agent 能互相发现并对话
- 协议三层：发现（DNS 级别）→ 会话管理 → 消息传递（基于 JSON-RPC）
- 每个 Agent 通过 `well-known` 目录声明自己的能力，类似网站发布 RSS 订阅
- 与 MCP 的关系：MCP 解决「工具接入」，A2A 解决「智能体协作」，两者互补
- A2A 不是模型层协议——它不改变模型能力，只是定义 Agent 间通信的标准

## Skills 机制

### 概念

Skills（技能）是 Anthropic 2025 年推出的概念，核心思想是把「任务知识固化」从每次对话时重新解释提示词，升级为可复用、可组合、可渐进式披露的「技能包」——就像手机 App Store 里的 App 一样，Skill 是可独立下载、独立更新、按需加载的知识模块，解决的是「同一个任务每次都要重新解释」的重复劳动问题。

### 核心机制

| 维度 | 说明 |
|---|---|
| **Skill 定义** | 结构化知识包，包含描述、触发条件、执行规则、示例，以 YAML 或 JSON 格式存储 |
| **渐进式披露** | 不是把所有技能一次性塞给模型，而是根据任务动态加载相关技能，节省上下文窗口 |
| **可组合性** | 多个 Skill 可以按任务需求组合使用，如「数据分析技能 + 可视化技能」组合 |
| **可编辑性** | Skill 是文本文件，支持版本控制、团队协作编辑、按需修改 |
| **KV 可组合缓存** | Skill 加载后可缓存为 KV 键值对，避免重复解析，提升加载速度 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| Skill Manifest | 技能清单文件，定义技能名称、版本、描述、触发条件 |
| Skill 模板 | 技能执行模板，包含输入参数、执行步骤、输出格式 |
| 触发条件 | 定义在什么情况下加载该 Skill（如文件名匹配、关键词匹配） |
| 渐进式披露 | 只在需要时加载相关 Skill，避免上下文窗口浪费 |
| KV 缓存 | Skill 加载后缓存为键值对，后续调用时直接复用，无需重新解析 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| Claude Code 内建 Skill | Claude 官方 Skill 系统 | 内建编程、测试、文档等 Skill，支持 `@skill-name` 触发 |
| OpenClaw Skill | OpenClaw 平台 Skill | 支持自定义 Skill 文件，通过 `skills/` 目录管理 |
| 本地 Skill 文件 | 自定义 Skill | 将 Skill 定义为 YAML/JSON 文件，放在项目目录下 |

### 要点速记

- Skill 是「可复用知识包」——定义一次，到处可用，避免重复解释
- 渐进式披露是核心——只在需要时加载，节省上下文窗口
- 可组合性——多个 Skill 可以组合使用，如「数据分析 + 可视化」
- KV 缓存——Skill 加载后缓存，避免重复解析，提升效率
- 与 MCP 的区别：MCP 是工具接入协议，Skill 是知识固化方式，两者互补
- 与模板的区别：模板是单次执行规则，Skill 是可持久化、可复用的知识模块

## Computer Use

### 概念

Computer Use 是让 LLM 像人类一样「操作电脑」的技术，核心思想是：不是通过 API 调用软件功能，而是通过「看屏幕截图 + 操作鼠标/键盘」来完成任何电脑上能做的事——包括浏览网页、编辑文档、运行程序、操作游戏等。这是 Agent 从「数字助手」迈向「通用数字员工」的关键一步。

### 核心机制

| 维度 | 说明 |
|---|---|
| **观察层** | 通过截图（Screenshot）获取屏幕视觉信息，分辨率通常为 1920x1080 或更高 |
| **操作层** | 模拟人类操作：鼠标点击、拖拽、键盘输入、滚动、快捷键等 |
| **决策层** | LLM 基于截图判断当前界面状态，决定下一步操作 |
| **闭环** | 截图 → LLM 分析 → 输出操作指令 → 执行 → 刷新截图 → 循环 |
| **安全层** | 沙箱隔离（虚拟机/容器）、操作审批门、操作日志记录 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| Screenshot API | 获取屏幕截图的接口，如 `pyautogui.screenshot()` |
| Mouse/Keyboard 模拟 | 模拟鼠标移动、点击、键盘输入的操作库 |
| Accessibility Tree | 可访问性树，比截图更结构化的界面元素描述 |
| 操作审批门 | 关键操作（如删除文件）前需要人工确认的安全机制 |
| 沙箱隔离 | 在虚拟机或容器中运行 Computer Use，防止误操作破坏系统 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| Claude Computer Use | Claude 官方 Computer Use | 支持网页浏览、文档编辑、程序操作，通过 API 集成 |
| OpenAI Computer Use | OpenAI 平台 Computer Use | 基于 GPT-4o，支持截图分析和操作生成 |
| AutoGPT / BabyAGI | 早期 Computer Use 探索 | 通过脚本+截图循环实现简单自动化 |
| 自定义 Computer Use | 本地实现 | 结合 `pyautogui`、`PIL`、LLM API 自行实现 |

### 要点速记

- Computer Use 的核心是「截图 + 操作」闭环——不看代码，只看屏幕
- 观察层：截图（视觉信息）或 Accessibility Tree（结构化信息）
- 操作层：鼠标/键盘模拟，支持点击、拖拽、输入、快捷键
- 安全是关键：沙箱隔离防止误操作，操作审批门防止危险操作
- 与 API 调用的关系：Computer Use 不依赖软件 API，而是模拟人类操作
- 当前瓶颈：截图信息冗余多，LLM 需要学会关注关键区域而非全图
- 典型应用场景：网页自动化、文档编辑、GUI 程序操作、游戏自动化

## 沙箱

### 概念

沙箱（Sandbox）是 Agent 执行代码的「隔离运行环境」，核心思想是：让不可信的代码（Agent 生成的代码、用户输入的代码）在隔离环境中运行，即使代码包含恶意逻辑，也无法破坏宿主机系统。这是 Agent 安全执行的第一步，也是 Computer Use 和代码执行场景的安全基础。

### 核心机制

| 维度 | 说明 |
|---|---|
| **隔离层** | 通过容器（Docker）、虚拟机（KVM/VMware）、或 microVM（Firecracker）实现进程级隔离 |
| **网络控制** | 可配置出站/入站网络规则，防止数据泄露或外部攻击 |
| **文件系统隔离** | 只读挂载、权限控制，防止 Agent 读写敏感文件 |
| **资源限制** | CPU、内存、磁盘、网络带宽限制，防止资源耗尽攻击 |
| **执行超时** | 强制终止长时间运行的进程，防止无限循环 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| Docker 容器 | 最常用的沙箱实现，通过 Docker Engine 隔离进程、文件系统、网络 |
| E2B | 托管云沙箱 API，通过 HTTP 发送代码，返回 stdout/stderr |
| Firecracker microVM | 轻量级虚拟机，启动时间 < 200ms，适合快速隔离执行 |
| seccomp 配置 | 限制系统调用，防止 Agent 调用危险系统函数 |
| cgroups | Linux 内核资源控制组，限制 CPU、内存、磁盘等资源 |
| 只读挂载 | 将文件挂载为只读，防止 Agent 修改敏感文件 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| Docker + E2B | 云端沙箱服务 | 通过 HTTP 提交代码，E2B 在 microVM 中执行并返回结果 |
| Modal | 云端计算平台 | 支持 GPU，适合需要运行 ML 工作负载的沙箱 |
| Docker 本地沙箱 | 本地实现 | 通过 `docker run` 启动容器，执行 Agent 代码 |
| E2B Python SDK | 本地 SDK | 提供 `E2BClient`，支持本地和云端两种部署方式 |

### 要点速记

- 沙箱是 Agent 安全执行的基础——隔离运行不可信代码
- 四层隔离：进程级（Docker/VM）、网络级（出站控制）、文件系统级（只读挂载）、资源级（CPU/内存限制）
- E2B 是主流云端沙箱服务，支持 HTTP 提交代码、microVM 执行、秒级启动
- 沙箱逃逸是主要攻击面：需纵深防御（容器 + seccomp + 只读根文件系统 + 网络出站过滤）
- 沙箱与 Computer Use 的关系：沙箱用于代码执行，Computer Use 用于 GUI 操作，两者互补
- 典型应用场景：执行 Agent 生成的代码、运行用户脚本、测试代码、数据分析

## 长程任务

### 概念

长程任务（Long-Running Task）是 Agent 需要连续运行数小时甚至数天的任务，核心思想是：不是单次对话，而是通过「循环执行 + 状态管理 + 外部记忆 + 终止控制」的完整循环工程架构，让 Agent 在无人值守的情况下持续工作、自我修正、逐步推进，最终完成任务。

### 核心机制

| 维度 | 说明 |
|---|---|
| **循环架构** | ReAct 循环（思考→行动→观察）或 Plan-Execute-Verify 循环，持续迭代直到任务完成 |
| **状态管理** | 外部持久化存储（数据库/文件），记录当前进度、已完成步骤、失败历史 |
| **终止控制** | 硬性迭代上限、预算耗尽、无进展检测、目标达成四种退出条件 |
| **上下文管理** | 压缩策略（周期摘要、滑动窗口、外部记忆）、预算分配，防止上下文窗口劣化 |
| **失败恢复** | 从检查点恢复、策略记忆（记录失败的策略而非仅记录失败动作）、子 Agent 隔离 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| ReAct 循环 | Reason（推理）→ Act（行动）→ Observe（观察）的循环模式 |
| Reflexion | 反思循环，失败后写入自然语言反思，后续尝试读取反思避免重复错误 |
| 子 Agent | 分解长程任务为多个子任务，每个子任务由独立 Agent 执行 |
| 上下文压缩 | 周期摘要、滑动窗口、重要性加权，管理长循环中的上下文窗口 |
| 检查点 | 任务执行过程中的状态快照，支持从中恢复 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| Anthropic 长程任务 | Claude 官方长程任务支持 | 支持小时级持续运行，内置状态管理和错误恢复 |
| OpenClaw 常驻编排器 | 长期运行编排器 | 按固定周期运行，监控子循环、分派工作、崩溃恢复 |
| AutoResearch | 实验循环 | 修改训练脚本 → 限时实验 → 评估 → 决策（提交/回滚）→ 记录 |
| 夜间维护循环 | 自动化脚本 | 按 cron 计划运行，分类 CI 失败 → 修复 → 审查 → 通知 |

### 要点速记

- 长程任务的核心是「循环工程」——思考→行动→观察→反思，持续迭代
- 状态管理是一等公民——外部持久化存储记录进度、失败历史、交接上下文
- 终止控制是关键——硬性上限、预算耗尽、无进展检测、目标达成四种退出条件
- 上下文劣化是主要风险——通过压缩策略（周期摘要、滑动窗口、外部记忆）管理
- 与单次对话的区别：长程任务需要循环架构、状态持久化、失败恢复、终止控制
- 典型应用场景：代码仓库维护、CI 修复、实验自动化、数据批量处理、持续研究

## Harness Engineering

### 概念

Harness Engineering（编排工程）是 2026 年 3 月 Anthropic 提出的概念，核心思想是：让 LLM 变成可靠的 Agent，关键不在于模型本身有多强，而在于「围绕模型的运行时环境设计」——包括上下文管理、工具集成、错误处理、可观测性等——就像优秀的赛车手需要优秀的赛车一样，优秀的 Agent 需要优秀的 Harness。

### 核心机制

| 维度 | 说明 |
|---|---|
| **上下文管理** | 预算分配（系统提示 10-15%、历史 30-40%、生成 20-30%）、动态压缩、Token 计数 |
| **Prompt 即代码** | Prompt 需要版本控制、测试、模块化组装，像代码一样管理 |
| **工具执行器** | 沙箱执行、重试逻辑、输出截断、人机协同审批门 |
| **循环检测** | 滑动窗口哈希检测重复动作，防止死循环 |
| **错误处理** | 优雅恢复、超时控制、指数退避、丰富错误信息 |
| **可观测性** | 从第一天就埋点追踪，记录输入/输出/成本/延迟 |

### 关键术语/接口

| 术语 | 含义 |
|---|---|
| Context Manager | 上下文管理器，负责 Token 预算分配、历史压缩、Token 计数 |
| Tool Executor | 工具执行器，负责沙箱执行、重试、截断、审批 |
| Loop Detector | 循环检测器，滑动窗口哈希检测重复动作 |
| Harness | 编排器，整合上下文管理、工具执行、循环检测、错误处理的完整运行时 |
| 可观测性 | 追踪、指标、日志——让 Agent 的行为可观察、可分析、可调试 |

### 常见实现/框架

| 框架 | 定位 | 要点 |
|---|---|---|
| OpenClaw Harness | 生产级 Harness 实现 | 整合上下文管理、工具执行、循环检测、可观测性 |
| LangSmith | 可观测性平台 | 追踪、评估、优化、A/B 测试、提示词版本管理 |
| LangChain | 基础 Harness 框架 | 提供 Agent 基础框架，支持工具集成和循环控制 |
| 自定义 Harness | 本地实现 | 基于 `AgentHarness` 类自行扩展，按需定制 |

### 要点速记

- Harness 是「Agent 的运行时环境」——整合上下文管理、工具执行、循环检测、错误处理
- 上下文是有限资源——显式强制预算，使用模型精确的 tokenizer 计数 Token
- Prompt 即代码——版本控制、测试、模块化组装，像代码一样管理
- 工具是 Agent 的执行器——精确定义、沙箱化执行、防御性处理输出
- 编排模式不能一刀切——探索性任务用 ReAct，结构化任务用 Plan-Execute，复杂任务用多 Agent
- 状态管理是一等关注点——提前设计状态 schema；事后改造非常痛苦
- 错误是不可避免的——优雅恢复是一项特性——实现重试逻辑、循环检测、丰富错误信息
- 可观测性不是可选项——你无法调试看不见的东西——从第一天就埋点追踪
