# Agent 架构与工程：六大核心问题拆解

> 从「什么是 Agent」一路讲到「怎么把 Agent 安全、便宜、稳定地跑在生产环境」。这份笔记整理了 Agent 工程中最常被问到的六个问题，每个问题都按「一句话回答 → 白话解读 → 要点拆解 → 面试速记」展开，适合快速复习和面试前过一遍。

---

## 1. 什么是 Agent 应用？C 端 Agent 应包含哪些模块？

### 一句话回答

Agent 应用 = LLM（大脑）+ 上下文（记忆）+ 工具（手脚），通过「思考 → 行动 → 观察」的循环自主完成任务；面向普通用户的 C 端 Agent，还要额外补齐交互、记忆、安全这些工程模块。

### 白话解读

Agent 不是一个新模型，而是「模型 + 记忆 + 工具」拼出来的一个系统。模型负责想，记忆负责记住上下文，工具负责动手。它跟普通聊天机器人的本质区别是：聊天机器人一问一答，Agent 会自己循环推进任务——想一步、做一步、看结果、再想下一步，直到完成。

- **LLM（大脑）**：负责推理和决策，决定「下一步做什么」。
- **上下文（记忆）**：对话历史、检索到的文档、工具返回的结果、当前状态，都是喂给模型的上下文。
- **工具（手脚）**：搜索、计算、执行代码、读写文件，通常通过 MCP 协议接入。

**Agent 和 Workflow 的分界线**：判断标准只有一条——「控制权在代码手里，还是在模型手里」。Workflow 的每一步是代码写死的；Agent 的每一步由模型动态决定。所以 Workflow 可预测、成本低，但只能处理结构已知的任务；Agent 灵活，但不可预测、成本高。**能用一个简单 Workflow 解决的问题，就不要上 Agent。**

C 端 Agent 跟内部工具型 Agent 不一样，它直接面对海量普通用户，所以还要补三块：**交互体验**（多模态、流式、可打断）、**用户记忆**（长期画像和偏好，注意隐私边界）、**安全护栏**（危险操作必须人工确认）。

### 要点拆解

**C 端 Agent 应包含的模块**

| 模块 | 作用 | 要点 |
|---|---|---|
| 对话与交互层 | 多模态输入输出、流式响应、可打断 | C 端体验的核心，需支持富文本 / 语音 / 图片 |
| 上下文管理 | 历史会话、预算分配、压缩 | 系统提示占 10-15%、历史 30-40%、生成预算 20-30% 且优先保留 |
| 工具接入层 | 统一调用搜索 / 日历 / 备忘录等 | 用 MCP 协议标准化接入，支持动态发现 |
| 记忆系统 | 短期（会话内）与长期（用户画像、偏好） | 用户级记忆必须设计好隐私边界 |
| 规划模块 | 把目标拆成子任务再执行 | 简单任务单轮工具调用即可，复杂任务才用 Plan-Execute |
| 安全护栏 | 内容安全、操作审批门、敏感信息保护 | 删文件、付费等危险操作必须人工确认 |
| 成本控制 | Token 预算、模型分级路由 | C 端量大，需小模型兜底 + 缓存（详见问题 4） |
| 可观测性 | 埋点、日志、用户行为分析 | 你无法调试看不见的东西 |

### 面试速记

- 一句话公式：**Agent = LLM + 上下文 + 工具**（李博杰）
- 分界线就一句：**控制权归代码还是模型**
- C 端三个差异化模块：**交互体验、用户记忆、安全护栏**
- 原则：**先 Workflow 后 Agent**，能用简单架构解决的别上复杂 Agent

## 2. 当前 Agent 系统最大的工程挑战是什么？

### 一句话回答

最大的挑战是把 Agent 从「Demo 能跑」变成「生产级可靠」——集中在上下文管理、可靠性评估、成本失控、安全隔离四个问题上，本质是「聊天机器人评估」和「Agent 评估」之间存在鸿沟。

### 白话解读

做一个能跑通的 Demo 不难，难的是让它稳定跑几个月不出事。挑战可以浓缩成四个字：

- **上下文**：任务一长，对话窗口就被历史塞满，模型开始「中间迷失」，还会重复已经失败过的方法。
- **可靠性**：怎么评价一个 Agent 好不好？聊天机器人看单次回复质量就够了，但 Agent 要看「能不能在多步长任务里稳定达成目标」，这两套评估方式之间有巨大鸿沟。
- **成本**：一个失控的循环一夜就能烧掉几百美元，重试还会让成本线性放大。
- **安全**：Agent 会生成代码、操作界面，可能破坏宿主系统或泄露数据。

其中最容易踩坑的是两个「看起来像努力、其实是偷懒」的失败模式：**Reward Hacking**（靠删掉测试让 CI 变绿，骗过评估指标）和 **Loopmaxxing**（靠堆轮数假装变强，而不是真的变强）。应对之道是四个纪律：**显式终止 + 确定性验证 + 预算约束 + 制造者与检查者分离**（让写答案的和验收的分开，别自己给自己打分）。

### 要点拆解

| 挑战 | 表现 | 应对方案 |
|---|---|---|
| 上下文窗口管理 | 长任务中窗口被历史填满、「中间迷失」；重复已失败的方法 | 压缩策略（周期摘要 / 滑动窗口 / 外部记忆）、显式 Token 预算、子 Agent 隔离 |
| 可靠性 / 评估鸿沟 | 单次回复质量无法刻画长时程的目标达成率 | 专用环境 + 基准（SWE-bench / WebArena）、确定性验证优先、LLM-as-judge 兜底 |
| 循环失控 | 死循环、Reward Hacking、Loopmaxxing | 循环检测（滑动窗口哈希）、终止工程（硬上限 / 预算 / 无进展检测）、制造者-检查者分离 |
| 成本失控 | 长循环一夜烧掉数百美元；重试线性放大成本 | 提示缓存、预算上限、模型分级路由（详见问题 4） |
| 安全隔离 | 生成代码 / 操作 GUI 可能破坏宿主、泄露数据 | 沙箱（容器 / microVM）、审批门、网络出站过滤（详见问题 5） |
| 状态持久化 | LLM 两次调用之间无状态，长任务一中断就「失忆」 | 外部状态文件 / 数据库：进度追踪、失败记忆、交接上下文 |
| 可观测性不足 | 看不见就无法调试循环 | 从第一天埋点：run_id 追踪、结构化日志、成本 / 延迟指标 |

**评估鸿沟（关键认知）**

- 聊天机器人评估：衡量单次生成质量（流畅度、事实性）——基础设施简单。
- Agent 评估：衡量 Policy 质量（能否在多样长时程任务中稳定达成目标）——需要环境、基准、沙箱。
- 推动评估演进的三股力量：安全探索、可复现评估、课程学习。

### 面试速记

- 挑战就四个字：**上下文、可靠性、成本、安全**
- 两个经典失败模式：**Reward Hacking**（删测试骗过 CI）、**Loopmaxxing**（堆轮次代替能力）
- 四条工程纪律：**显式终止 + 确定性验证 + 预算约束 + 制造者与检查者分离**
- 金句：循环放大工程能力，但不取代工程能力；验证质量决定收敛质量

## 3. 设计一个通用 Agent Runtime 兼容多个模型厂商，如何抽象？

### 一句话回答

核心思路是「厂商无关 + 能力差异适配」：对上暴露统一的消息 / 工具 / 调用接口，对下用适配器抹平各家 API 的差异，并对结构化输出、流式、function calling 等能力做分级降级。

### 白话解读

问题本质是：OpenAI、Anthropic、Gemini、各家开源模型，API 长得都不一样，怎么让你的 Agent 代码不用为每个厂商重写一遍？答案是加一层「统一接口 + 适配器」。

- **对上层**：你的 Agent 逻辑只跟一套统一接口打交道（统一的消息格式、统一的工具定义、统一的 `chat()` 调用），完全不知道底层是哪个厂商。
- **对下层**：用一个适配器（Adapter）把各家 API 的差异翻译成统一格式。

难点不在「格式统一」，而在**能力参差不齐**：有的模型原生支持 function calling，有的不支持；有的支持结构化输出，有的不支持；上下文长度从 4K 到 1M 都有。所以 Runtime 要做一个「能力分级 + 降级」机制：模型不支持某项能力时，自动降级（比如不支持 function calling 就退回「让模型输出 JSON 再解析」）。

另外一个关键点是**两层解耦**：模型接入用 Adapter，工具接入用 MCP（Model Context Protocol）。这样换模型厂商、换工具都不会互相影响。

### 要点拆解

**抽象分层（参考漫游指南第 18 章 Harness 设计）**

```
┌─────────────────────────────────┐
│  Agent 应用层（规划 / 工具 / 记忆）  │  ← 只依赖统一接口
├─────────────────────────────────┤
│  统一模型接口层（Runtime 核心）    │  ← Message / ToolDefinition / 调用与流式
├─────────────────────────────────┤
│  厂商适配器（Adapter）            │  ← OpenAI / Anthropic / Gemini / 开源
└─────────────────────────────────┘
```

**四类统一抽象**

| 抽象对象 | 统一方式 | 要点 |
|---|---|---|
| 消息格式 | 统一 Role + Content + tool_calls + tool_call_id | 各家 System / User / Assistant / Tool 语义一致，映射为内部 dataclass |
| 工具定义 | 统一 JSON Schema（name / description / parameters） | 各家 function calling 格式不同，转换在适配层完成 |
| 调用接口 | 统一 `chat(messages, tools) -> response` | 同步 / 异步 / 流式三种模式一致化 |
| 能力声明 | 能力分级（Capabilities） | 结构化输出、并行工具调用、流式、长上下文——不支持则降级或报错 |

**能力差异适配（关键工程点）**

| 能力 | 厂商差异 | 适配策略 |
|---|---|---|
| Function Calling | OpenAI / Anthropic 原生支持，部分开源模型不支持 | 不支持时降级为「输出 JSON / 特殊标记再解析」 |
| 结构化输出 | 各家支持程度不同 | 统一走 JSON Schema 校验，解析失败重试 1 次 |
| 流式 | SSE 格式各异 | 适配层统一转成标准事件流 |
| 上下文长度 | 4K ~ 1M 不等 | Runtime 按模型能力分配预算，超限自动压缩 |
| 价格 / 速度 | 差异大 | 暴露统一的模型路由配置，按任务类型选模型 |

**与 MCP 的关系**

- MCP 解决「工具接入」的标准化：统一客户端 ↔ 服务器，一个 MCP 服务器可服务多个 LLM 平台。
- Runtime 内嵌 MCP Client，让工具发现与调用跟模型厂商解耦。
- 模型层（各家 API）+ 工具层（MCP）双标准化，是当前主流架构。

### 面试速记

- 抽象三件套：**统一消息格式、统一工具 Schema、统一调用接口**
- 关键设计：**能力分级 + 降级策略**（不支持 function calling 就退回解析式）
- 工具接入用 **MCP**，模型接入用 **Adapter**，两层解耦
- 加分项：温度 / 结构化输出等参数也要归一化，避免厂商特有参数泄漏到上层

## 4. 大规模部署时 Token 成本怎么控制？

### 一句话回答

核心是三条线「减少重复计费 + 压缩无效消耗 + 分级使用模型」：提示缓存复用不变上下文、压缩 / 截断工具输出、用小模型路由简单任务，并给每次运行设硬性预算上限。

### 白话解读

成本可以看成一个乘法公式：

```
成本 ≈ 迭代轮数 N × 每轮 Token 数 T × 单价 p  （再加上工具成本和验证成本）
```

三个乘数都能优化，对应三条路：

- **降低 N（少跑几轮）**：用更好的验证信号和终止工程，避免空转和死循环。
- **降低 T（每轮少喂点）**：压缩历史、截断工具输出。
- **降低 p（单价更低）**：用提示缓存、用小模型跑简单任务。

其中收益最大、最优先做的是**提示缓存**：循环里系统提示、目标定义、早期历史跨轮不变，这些不变的部分按缓存价计费，通常能覆盖 60-80% 的上下文。另一个容易被忽视的「不变量」是**生成预算优先预留**——先给生成预留 20-30% 的窗口，再填其他内容，别让历史把生成空间挤没了。最后一定要设**硬性预算上限**：预算耗尽就「保存状态 → 升级人工」，绝不允许无界执行。

### 要点拆解

**成本模型（漫游指南 19.12 循环经济学）**

```
Cost_loop = N（迭代轮数）× T（每轮 token）× p（单价） + 工具成本 + 验证成本
```

| 杠杆 | 作用点 | 典型收益 |
|---|---|---|
| 减少 N | 更好的验证信号、终止工程 | 避免空转与死循环 |
| 减少 T | 压缩历史、截断工具输出 | 单轮成本线性下降 |
| 降低 p | 提示缓存、模型分级 | 缓存部分按更低费率计费 |

**六大控制手段**

| 手段 | 原理 | 落地要点 |
|---|---|---|
| 提示缓存（Prompt Caching） | 系统提示 / 早期上下文跨迭代不变，按缓存价计费 | 循环中通常 60-80% 上下文可缓存；目标定义、技能内容、早期历史保持稳定 |
| 上下文压缩 | 周期摘要、滑动窗口、外部记忆 | 每 k 步摘要历史；只留最近 w 步；细节写文件、上下文只留引用 |
| 工具输出截断 / 摘要 | 长输出（日志 / 文件列表）进上下文前先压缩 | Tool Executor 设 MAX_OUTPUT_TOKENS（如 2000），超出截断并标注 |
| 模型分级路由 | 简单任务用小模型 / 快模型 | 分类器路由：客服分诊、简单问答走小模型，复杂推理走大模型 |
| 预算硬上限 | 每次运行设 token / 时间 / 金钱上限 | 预算耗尽触发「保存状态 → 升级人类」，禁止无界执行 |
| 批量与复用 | 批处理推理、KV Cache 复用 | 服务端 KV Cache 减少重复 prefill 计算 |

**上下文预算分配（参考基线）**

| 组件 | 预算 | 说明 |
|---|---|---|
| 系统提示 | 10-15% | 稳定；定义角色、工具、约束 |
| 检索文档 / RAG | 20-30% | 动态；每轮刷新 |
| 对话 / 动作历史 | 30-40% | 随运行变长而压缩 |
| 生成预算 | 20-30% | **优先预留，绝不可压缩低于此线** |

### 面试速记

- 成本公式：**成本 = 轮数 × 每轮 token × 单价**——三个乘数都能优化
- 最优先手段：**提示缓存**（60-80% 可缓存，直接降单价）
- 关键词：**压缩、截断、路由、预算、缓存**
- 金句：没有预算上限的失控循环，一夜就能烧掉几百美元
- 加分项：提到「生成预算优先预留，先留 20-30% 再填其他」这一不变量

## 5. Agent 生成代码并在沙箱执行，安全怎么设计？

### 一句话回答

安全设计的核心是「纵深防御 + 最小权限」：Agent 生成的代码在隔离环境（容器 / microVM）中运行，同时限制网络、文件系统、资源与系统调用，再加超时与人工审批门，任何单一防线被突破仍有兜底。

### 白话解读

Agent 生成的代码不可信，所以不能让它直接在宿主机上跑。思路是「层层设防」：就算某一层被突破，还有下一层兜底。

隔离强度从轻到重有四档：**进程级**（子进程 + 资源限制，快但弱）→ **容器**（Docker + seccomp + cgroups，中等）→ **microVM**（Firecracker / Kata，强且快，Firecracker 启动 <200ms）→ **虚拟机**（KVM，最强但慢）。

除了隔离本身，还要在**网络、文件系统、资源、系统调用**四个方向收口：出站网络白名单（防数据外渗）、只读根文件系统（防改敏感文件）、cgroups 限额（防资源耗尽）、seccomp 白名单（防危险系统调用）。最后加两道流程控制：**审批门**（危险操作如 `run_python` 必须人工确认）和**超时终止**（防死循环）。

一句话记住原则：**绝不以宿主级权限运行 Agent 生成的代码**。行业里 E2B（托管云沙箱，Firecracker microVM）、Modal（托管执行 + GPU）都是现成方案。另外注意：代码执行走沙箱，GUI 操作走虚拟桌面，两者安全原则一致。

### 要点拆解

**隔离层级（从轻到重）**

| 层级 | 技术 | 隔离强度 | 启动速度 |
|---|---|---|---|
| 进程级 | 子进程 + 资源限制 | 低 | 快 |
| 容器 | Docker + seccomp + cgroups | 中 | 较快 |
| microVM | Firecracker / Kata | 高 | <200ms（Firecracker） |
| 虚拟机 | KVM / VMware | 最高 | 慢 |

**六大防线（纵深防御）**

| 防线 | 机制 | 防什么 |
|---|---|---|
| 容器 / microVM 隔离 | 每个任务全新实例，结束即销毁 | 宿主系统破坏、跨任务污染 |
| 网络出站过滤 | 白名单域名、禁用外联 | 数据外渗、恶意下载 |
| 文件系统只读 | 只读根文件系统、受控挂载点 | 读写敏感文件、篡改配置 |
| 资源限额 | cgroups 限制 CPU / 内存 / 磁盘 | 资源耗尽攻击、挖矿 |
| 系统调用限制 | seccomp 白名单 | 危险 syscall（内核提权） |
| 执行控制 | 超时强制终止、输出截断 | 无限循环、输出爆炸 |

**流程控制**

| 环节 | 设计 | 要点 |
|---|---|---|
| 审批门 | 危险工具（run_python 等）requires_approval | 按工具粒度而非运行粒度，细粒度控制 |
| 重试与退避 | 超时 / 失败指数退避重试 | 最多重试 N 次，避免放大攻击面 |
| 输出处理 | 防御性截断与清洗 | 防止工具输出注入上下文误导模型 |
| 审计日志 | 记录完整调用链 | run_id 追踪，可回放、可取证 |

### 面试速记

- 一句话：**纵深防御 + 最小权限 + 沙箱隔离**
- 五道防线默背：**容器隔离、网络过滤、文件只读、资源限额、seccomp**
- 两个必提点：**审批门**（危险操作人工确认）、**超时终止**（防死循环）
- 加分项：E2B / Firecracker（启动 <200ms）、「沙箱逃逸是主要攻击面，需多层组合而非单点」
- 与 Computer Use 的关系：代码执行走沙箱，GUI 操作走虚拟桌面，安全原则一致

## 6. 对接企业知识问答 Agent，飞书、钉钉、邮件怎么统一接入？

### 一句话回答

核心是「渠道适配器 + 统一事件模型」：把飞书 / 钉钉消息、邮件全部归一化为统一的消息事件，进入同一个异步消息队列，由 Agent 处理后统一回调各渠道；不同渠道的差异全部收敛在适配层。

### 白话解读

飞书、钉钉、邮件的消息格式、回调方式各不相同，如果 Agent 核心逻辑跟每个渠道强耦合，每接一个新渠道都要改核心代码。解法是加一层「渠道适配层」：

1. **收**：飞书 Webhook、钉钉 Webhook、邮件（POP / IMAP）各自的消息，先被适配层翻译成统一的消息事件（sender / channel / msg_type / content / message_id）。
2. **处理**：统一事件进入异步消息队列，Agent 消费队列统一处理（这里是 RAG 知识问答）。
3. **回**：处理结果按 message_id 回写到对应渠道（飞书 / 钉钉走 bot 消息 API，邮件走 SMTP 回复）。

三个渠道各记住一个关键词：**飞书**（卡片消息、@回复）、**钉钉**（stream 长连接，免公网回调）、**邮件**（线程 subject 匹配 + 附件解析）。

工程上要守三个底线：**幂等**（用 message_id 去重，防止 webhook 重试导致重复问答）、**异步削峰**（长任务先回「正在处理」，完成后推送结果）、**权限与脱敏**（谁能查哪些知识、消息脱敏后才入上下文）。

### 要点拆解

**总体架构**

```
飞书Webhook ─┐
钉钉Webhook ─┼→ 渠道适配层 → 统一消息事件 → 消息队列 → Agent 核心（RAG 问答）
邮件(POP/IMAP)┘      ↑                                      ↓
             各渠道回调 API ←—— 统一响应事件 ←—— 队列/直连分发
```

**统一接入四要素**

| 要素 | 设计 | 要点 |
|---|---|---|
| 消息归一化 | 渠道消息 → 统一事件（sender / channel / msg_type / content / message_id） | 文本、图片、@提及、会话上下文统一字段 |
| 异步队列 | 事件源 → 队列 → 消费者（Agent） | 削峰、重试、断点恢复（事件驱动异步 Agent 架构） |
| 回调 / 回复路由 | 响应按 message_id 回写对应渠道 | 各渠道回复 API 不同（飞书 / 钉钉 bot 消息、邮件回复） |
| 身份与权限 | 统一用户映射、租户隔离、知识库权限 | 企业场景合规底线：谁的问题能查哪些知识 |

**渠道适配器职责**

| 渠道 | 接收方式 | 回复方式 | 适配要点 |
|---|---|---|---|
| 飞书 | Webhook / 事件订阅 | bot 消息 API | 卡片消息、@回复、消息线程 |
| 钉钉 | Webhook / stream 模式 | robot 消息 API | 支持 stream 长连接，免公网回调 |
| 邮件 | IMAP 拉取 / 企业邮箱 API | SMTP 回复 | 邮件线程（subject 匹配）、附件解析 |

**与 RAG / 知识问答的结合**

- Agent 核心面向「知识库检索 → 生成回答」，渠道只是收发壳，逻辑与渠道解耦。
- 长任务（如「汇总本周所有报销邮件」）走异步：先回「正在处理」，完成后推送结果。
- 参考《深入理解 AI Agent》第 4 章事件驱动异步 Agent：事件源 + 队列 + 取消式 / 队列式 / 并行式处理，支持打断与恢复。

**工程要点**

| 关注点 | 方案 |
|---|---|
| 幂等 | message_id 去重，防止 webhook 重试导致重复问答 |
| 重试 | 队列消费失败指数退避，死信队列人工处理 |
| 限流 | 按渠道限流，防止 Agent 超载 |
| 敏感信息 | 邮件 / 消息脱敏后入上下文；不落明文日志 |
| 统一状态 | 同一用户跨渠道的会话状态管理（是否共享上下文） |

### 面试速记

- 一句话：**渠道适配层把异构消息统一成事件，进队列，Agent 统一处理，再回调分发**
- 三个渠道三个词：飞书（卡片）、钉钉（stream）、邮件（线程 + 附件）
- 必提工程点：**异步队列削峰、message_id 幂等去重、权限 / 脱敏**
- 加分项：「渠道只做收发壳，知识问答逻辑与渠道解耦；长任务异步化：先应答后推送」
- 与 MCP 的关系：企业内部知识源也可通过 MCP 服务器暴露，渠道层与知识层彻底解耦
